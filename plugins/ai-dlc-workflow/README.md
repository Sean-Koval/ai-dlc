# AI-DLC workflow plugin

One optional Claude Code plugin, with a Codex form, that carries AI-DLC's
workflow guidance, team skills and safety hooks. A team harness pins it as a single component, so a run
can be compared with and without it. AI-DLC authors the plugin; it does not
decide where it is enabled.

Everything in this directory except this README is generated by
`scripts/build_workflow_plugin.py` from `agents/skills/`, the shared AGENTS.md
guidance and `src/ai_dlc/harness/hook_shim.py`. Do not edit generated files;
change the source and rebuild. The `generated` required check runs the builder
with `--check`.

## What is inside

| Path | Content |
| --- | --- |
| `skills/ai-dlc-workflow/` | Provider-neutral workflow guidance as a skill; plugin `CLAUDE.md` files are not loaded |
| `skills/<team-skill>/` | discovery, prd-draft, needs-spec, spec-from-prd, review-inbox, handoff, document-review, document-organize, design-brief, design-evaluate |
| `hooks/hooks.json` | SessionStart, PreToolUse (`Bash\|exec_command`) and Stop hooks, exec form, 10 s timeout |
| `hooks/aidlc_hook.py` | Standard-library hook shim |
| `plugin.lock.json` | One digest per component, a `content_digest` over them, the digest of every published file, and the Codex form's digests |
| `native/codex/` | The Codex form (below); not part of the Claude plugin a harness publishes |

Skills appear namespaced, for example `ai-dlc-workflow:needs-spec`. The personal
`day-start` and `day-end` skills are not included. When a repository also renders
its own unprefixed copies, the guide skill tells the agent to prefer those.

`plugin.json` sets `version` to `<engine>-r<revision>`. The builder increases the
revision whenever the content digest changes, so installed copies update only when
content changes. `metadata.content_digest` repeats the lock's digest; the pinning
harness records the source commit.

## Codex form

`native/codex/` is generated by the same builder:

| Path | Content |
| --- | --- |
| `skills/<name>/SKILL.md` | The same bytes as the Claude plugin's skills (same digests), guide included |
| `hooks.json` | SessionStart, PreToolUse and Stop in the `.codex/hooks.json` shape, running the shim as `python3 "${PLUGIN_ROOT:-${CODEX_HOME:-$HOME/.codex}/ai-dlc-workflow}/hooks/aidlc_hook.py" <event>` |
| `hooks/aidlc_hook.py` | The same shim |
| `AGENTS.fragment.md` | The guide skill's body, for harnesses that only read AGENTS.md |
| `.codex-plugin/plugin.json` | A Codex local-plugin manifest (`skills: ./skills/`, `hooks: ./hooks.json`) |

The directory works two ways: as a Codex local plugin listed in a marketplace, or
copied to `$CODEX_HOME/ai-dlc-workflow/` with `hooks.json` merged into
`$CODEX_HOME/hooks.json` (in a harness, `native/codex/ai-dlc-workflow/` maps there).

### Spike: Codex 0.162.1 (hangar's lock), 2026-10-17

Tested with `@openai/codex@0.162.1` in a scratch `CODEX_HOME`, a local marketplace,
and `codex exec` against a local stand-in for the Responses API that asks for one
`git reset --hard HEAD` shell call (read-only sandbox, no network model).

| Setup | Skills | Hooks |
| --- | --- | --- |
| Claude plugin (`.claude-plugin/`) installed in Codex | All 11 listed in the model-visible prompt as `ai-dlc-workflow:<name>` (`codex debug prompt-input`) | Events fire but Codex ignores exec-form `args`: the shim never runs, nothing is blocked, Stop fails |
| `native/codex/` as a `.codex-plugin` local plugin, hooks not yet trusted | All 11 listed | Skipped: Codex requires hook review before plugin or user hooks run |
| Same, trusted (`codex exec --dangerously-bypass-hook-trust` for the test) | All 11 listed | SessionStart adds the shim's status line to the context; PreToolUse returns "Command blocked by PreToolUse hook: Destructive operation denied by the ai-dlc workflow plugin"; Stop completes |
| `native/codex/` copied to `$CODEX_HOME/ai-dlc-workflow/`, `hooks.json` as `$CODEX_HOME/hooks.json`, trusted | Not loaded (native skills belong in `.agents/skills`) | Same results as the trusted plugin |

So Codex 0.162.1 local plugins carry both skills and hooks, and the builder emits
`.codex-plugin/plugin.json`. Codex hooks run only after they are trusted (the TUI
review, persisted trust, or the bypass flag for vetted automation); a harness that
ships them has to arrange trust, or the hooks are silently inactive.

## A/B in a team harness

`scripts/publish_workflow_plugin.py --harness-repo <harness dir> --dry-run|--apply`
copies this directory without `native/` to `<harness>/plugins/ai-dlc-workflow/`
and `native/codex/` to `<harness>/native/codex/ai-dlc-workflow/`. It refuses a
target that is not empty or an unmodified earlier publication, never touches other
files, and prints the component ids, digests (this lock's and hangar's directory
`files_digest`), the source commit and the marketplace entry
(`{"name": "ai-dlc-workflow", "source": "./plugins/ai-dlc-workflow", "defaultEnabled": false}`;
`version` in `plugin.json` overrides an entry's version). The change reaches the
harness repository by pull request; re-pin with its own tooling.

The experiment, owned by flightdeck:

- **Arm A**: the harness without the component.
- **Arm B**: the same harness plus `plugin:ai-dlc-workflow` and the Codex
  `native:codex/ai-dlc-workflow/*` files. Nothing else differs.
- Keep plugin `autoUpdate` `false` (`plugins: {autoUpdate: false}` in the lock) in
  experiment sandboxes, or the treatment can change mid-experiment.
- Hangar's harden mode drops plugins in `ask` and `deny-risky` turns. Run the arms
  in a turn mode where plugins load, or mount the plugin through hangar's read-only
  seed; otherwise arm B silently equals arm A. Flightdeck should confirm the turn-1
  manifest's effective skills include `ai-dlc-workflow:*` in arm B.
- For Codex arms, trust the hooks (above), or arm B gets the skills without the hooks.

## Hooks

The shim delegates to `ai-dlc hook <event>` only when `ai-dlc` is on PATH,
`ai-dlc.toml` exists at the repository root, and the session is not in a hangar
sandbox (`HANGAR_WORKSPACE` or `HANGAR_JOB_ID` set). Otherwise:

- SessionStart prints one line saying lifecycle commands are unavailable, or
  nothing with `AI_DLC_HOOKS=quiet`.
- PreToolUse denies destructive shell commands (such as `rm`, `git reset --hard`,
  `git clean -f`, force or delete pushes) with exit 2 and allows everything else.
  It never applies the bound-push policy, so `git push` and `gh pr create` are
  not blocked.
- Stop does nothing.

The shim reads only the command text, never runs it, and writes nothing to disk.
A failing or slow delegate is treated as allow with a one-line note, so a hook
never wedges a session.

## Requirements and limits

- `python3` (3.10 or later) must be on PATH. There is no shell fallback. Native
  Windows plugin hooks are unsupported because exec form cannot substitute another
  interpreter name.
- Hangar's hardened `ask` and `deny-risky` turns drop `enabledPlugins` and
  `extraKnownMarketplaces`, so the plugin does not load in those turns. Compare
  arms in turn modes where plugins load, or have hangar mount the plugin through
  `CLAUDE_CODE_PLUGIN_SEED_DIR`.
- Turn marketplace `autoUpdate` off wherever the plugin is installed for an
  experiment, or the treatment can change mid-experiment. Seed marketplaces are
  always read-only with auto-update off.
- The plugin declares no MCP servers and carries no credentials or project paths.

## Enable and disable

`defaultEnabled` is `false`, so the plugin loads only where it is enabled.

- Local testing: `claude --plugin-dir plugins/ai-dlc-workflow` together with
  `--settings '{"enabledPlugins": {"ai-dlc-workflow@inline": true}}'`.
- Marketplace install: set `"ai-dlc-workflow@<marketplace>": true` under
  `enabledPlugins` in the scope you want, or run
  `claude plugin enable ai-dlc-workflow@<marketplace>`.
- Turn it off: set the same key to `false`, or `claude plugin disable`.
- Keep the plugin but silence its hooks: `AI_DLC_HOOKS=off`.

Check the package with `claude plugin validate --strict plugins/ai-dlc-workflow`.
