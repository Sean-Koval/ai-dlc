## Context and observed behavior

`project adopt` already previews by default; `machine enroll` resolves reviewed source/ref and can populate an inactive cache; `machine plan/apply`, `project setup`, `agents render` and offline `project readiness` have distinct owners. `README.md` currently follows engine source bootstrap with engine `project check --required`. `MachineManager.status` is enrollment-only, and readiness never qualifies a native client. This design composes those responsibilities, retaining engine contributor instructions as a separate route.

## Reviewed interface

Add `ai-dlc project onboard --root PATH` as a **read-only plan**, without an apply flag. `--root` is required and must resolve to an existing readable target directory; there is no current-directory default. Missing, nonexistent or unreadable targets yield a bounded error without creating directories. An explicit engine-checkout root produces a consumer-versus-contributor warning requiring a distinct target selection for this consumer route. Optional inputs are `--source SOURCE --ref REF --profile-id ID --machine-id ID`, `--agent-client CLIENT` (repeatable), and `--preset generic|python`. Explicit target configuration wins over absent inputs; conflicting explicit selections are blockers rather than implicit rewrites. Source/ref/profile form one selection: incomplete values yield `input-required`. Current enrollment may satisfy that selection only when reported with its exact lock identity. A fresh target requires explicit client selection; an adopted target supplies clients from its own configuration. No engine repository settings are imported. Detect host OS/architecture and current shell; unknown shell means no copy-paste command for that action.

Return schema 1 JSON with `target` (local display root), `platform` (os, architecture, shell), `clients`, `engine` (version and known source identity, unknown allowed), `enrollment` (unselected, explicitly selected or locally verified identity, separate from engine provenance), `state` (`actionable`, `input-required`, `unsupported`, `blocked`), `findings[]` (`code`, `component`, `reason`, `next_action_id`), `actions[]` (`id`, `stage`, `depends_on`, `operation`, `argv`, `effects`, `requires_review`, `available`), and `qualification: not-assessed`. Actions use argument arrays as authority; shell-specific copy-paste text is derived only for supported shells. No source fetch, version probe, credential value access, or action execution occurs during this preflight. Engine version describes the running planner; the PATH-selected executable is reported separately with feature identity not-assessed. Recommendations are conditional on using the same reviewed engine environment, because PATH presence and an equal version string do not establish feature parity. Local paths stay local output; this is not the shareable export.

Ordered stages are install/activate engine (documentation when no engine exists), enroll the selected reviewed profile, preview/apply adoption for a fresh target, then preview/apply root-scoped machine changes when enrollment is selected, project setup, render preview/apply, offline readiness, and the target project's selected meaningful check. Adoption must precede root-scoped machine planning because that existing owner requires the target ai-dlc.toml. Already adopted targets omit adoption; every apply operation remains separately reviewed. Dependencies suppress unavailable commands; unresolved placeholders are displayed as input requests, never runnable text. A consumer may deliberately skip enrollment if the project is self-contained; report that choice, do not invent a profile. Source checkout installation does not make the consumer a contributor or require engine full tests. Existing release installation guidance must identify features missing from v0.4.0 and recommend an exact reviewed source revision only when needed and supplied.

The service delegates planning to existing **read-only** resolvers and assembles documented invocations of existing mutating services. It must not call an enrollment preview merely to collect data because that preview can populate caches. If current services cannot expose a needed fact without effects, return unknown and a precise next action. The CLI delegates to the application service. This change adds no MCP surface or execute-plan tool. Existing commands retain all authorization, ownership, conflict and preview semantics.

Exit 0 means the plan can be acted on, not that setup completed; exit 1 means blocked, unsupported or missing input; exit 2 means malformed arguments/configuration. Stable finding codes include `target-required`, `selection-conflict`, `source-selection-incomplete`, `unsupported-platform`, `unsupported-shell`, `unsupported-client`, `engine-feature-unavailable`, `configuration-invalid`, and `guidance-conflict`.

## Unsupported and recovery behavior

The bootstrap-facing README/platform table must be reachable without successfully importing AI-DLC on Windows. It states native Windows is unsupported by the current candidate and gives no POSIX/WSL command unless the team explicitly selected a Linux environment. A locally running preflight uses the same truthful result. Unsupported optional components are identified separately from blocking core prerequisites. Missing engine, malformed project, unreadable root, or unknown client returns scoped remediation without creating files or falling back to the engine root. After an explicit external action, rerun preflight from observed current state; there is no persisted wizard or automatic resume.

## Verification, privacy and cost

Test fresh and existing Unix projects, independent profiles, incomplete inputs, conflicts, unknown shell/client, unsupported Windows, repeat runs, and no filesystem/network/process side effects. Verify a target acceptance command is recommended rather than the engine's full test suite. A disposable real Unix downstream exercise records the selected roots, manual step count, time to first target check, defects and limitations; no numeric savings are claimed before baseline. Windows desktop observation remains #53, not a gate falsely satisfied by mocked platform tests. No paid models or remote mutations are needed. Do not emit credential values, account guesses or private shell-file contents.
