Target is Windows 11 x64 on local NTFS, initially launched through inbox Windows PowerShell 5.1, without preinstalled Python, uv, mise or AI-DLC. Network access and policy-permitted execution/install locations are required. PowerShell 7, ARM64, network shares and all optional modules are not implicitly qualified. Git is a prerequisite to cloning; a downloaded source archive/bootstrap seed can reach prerequisite provisioning without an existing Git installation. Never label a GitHub-hosted Windows Server run as a Windows 11 desktop walkthrough.

## Bootstrap and verified identity

Add `scripts/bootstrap.ps1` and its project-template counterpart. Provide native `-Source`, `-Plan`, `-Target`, `-Root` and `-PublishAliases` equivalents with consistent semantics. Plan validates inputs/OS and describes versions, sources, install destinations, PATH changes and unavailable selections without downloads or writes. Default remains verified release mode; source mode is an explicit developer/qualification route and records exact checkout/revision provenance.

Use reviewed pinned Windows x64 uv and mise assets with SHA256 verification before extraction or execution. Add a generated inert Windows pin artifact under `bootstrap/` with source/template equivalence checks; record upstream artifact URLs, versions, architecture and checksums rather than copying Unix hashes or selecting `latest`. Python is the explicit project/bootstrap pin provisioned through verified uv; require its upstream integrity verification rather than inventing a checksum for a different distribution. Reusing a cache entry requires checking its configured digest. HTTPS download redirects must not permit a downgrade to HTTP. Reject unsafe archive entries before extraction.

Keep the existing release wheel and hashed constraints identity. PowerShell reads `bootstrap/release.sh` as a restricted allowlisted data format; it must not execute or dot-source shell content. Validate every required key, HTTPS URL, digest, version and filename and reject unexpected executable expressions or duplicates. Retain the manifest byte-for-byte beside the installed engine and propagate it under the existing RP-02 contract. This avoids a parallel release identity format. Source installations without a release manifest remain honestly unable to distribute verified release bootstrap. A release carrying structured argv templates must require an engine containing the portable-core extension; old 0.4.0 assets are not retroactively labeled native-ready.

Stage downloads and installed tools independently in destination-local owned paths. Hold the appropriate portable lock around publication/selection, not unbounded remote downloads. Verify the new environment/entry points before changing the selected CLI. Preserve previously working executables on digest mismatch, install failure or sharing violations, and report retained failed staging. Native Windows may refuse replacement of an in-use executable; preserve and retry after release of that handle instead of deleting it. Unix open-reader publication remains unchanged. Do not claim full multi-tool transactional rollback; report any successfully prepared but unselected prerequisites and retain the previous working CLI selection.

## Native locations and activation

Respect explicit `AI_DLC_BOOTSTRAP_HOME`; otherwise use a current-user local application-data AI-DLC directory. Handle spaces/non-ASCII paths as data. Resolve environments through `Scripts/python.exe`, `Scripts/ai-dlc.exe` and the generated compatible alias entry point, not `bin/python` or Unix executable bits. Executable selection must use an actual runnable Windows `.exe` entry point, not a renamed text file or mandatory symlink. Reuse uv-created console launchers where their interpreter binding remains valid and verify that binding by execution before publication. Keep source environments per checkout, record their provenance, and preserve a working shared source selection unless explicit publication is requested or no working selection exists. Do not overwrite unrelated authored launchers.

Current-session activation is process-local and immediately usable. Permanent activation is a separately previewed/apply operation using the actual selected PowerShell profile location; create or update only the owned section, preserve unrelated bytes, refuse modified sections/reparse paths, and avoid duplicate PATH entries. Do not infer PowerShell from Unix `SHELL`. Document the direct absolute executable alternative and clean new-terminal verification. Do not alter machine PATH, execution policy, corporate restrictions or credentials. If policy blocks a profile/script, report that fact and a policy-approved/manual route instead of claiming activation succeeded.

## Minimal selected provisioning

The native `core` recipe supports Git and GitHub CLI (`git.exe` and `gh.exe`); `python` supports the pinned Python and uv toolchain with mise managing declared project runtimes. Bootstrap owns its verified uv/mise prerequisites. Reuse existing installations when they satisfy declared requirements, reporting observed versions rather than silently upgrading. For missing core applications, use an explicit reviewed `winget` plan with exact package IDs, source, scope and available version identity; never an unbounded upgrade. If winget is absent or a user-scope package is disallowed, block with named native manual-install guidance and rerunnable verification. No automatic elevation. No mandatory account login for local core/Python checks; selected provider auth remains separate.

Planning resolves selected modules and component-implied requirements. Unknown modules are errors. Known modules without a Windows recipe are listed individually as unavailable/unqualified. An unsupported unselected optional module does not block the minimal journey. A selected required unsupported module prevents complete readiness and must not be silently omitted; a supported subset may be prepared only if the plan/result explicitly states the incomplete selections. Sign-in hints are advisory and never account evidence. Do not make Windows native-client app provisioning a dependency of the minimum CLI setup.

## Generic/Python project flow

Consume the native argv contract supplied by `windows-portable-core`. Generic generated management checks use argv. A generic project has no invented behavioral test: adoption preserves the team's check; a walkthrough supplies a small real team-owned acceptance command to demonstrate success and deliberate failure. Python initialization keeps separate syntax and behavior checks and the existing missing/empty/all-skipped failure guarantees. For conditional lock creation/setup, prefer a small repository-owned Python helper invoked through argv with bounded existing semantics: initialization may generate a missing lock; noninitializing adoption requires the team's existing lock and never re-resolves silently. Checks themselves install nothing.

New starter templates must run on supported Unix as well as Windows; do not fork a second workflow language or mechanically translate authored shell scripts. Adoption without initialization preserves authored manifests/checks/tests and reports an explicit POSIX prerequisite if selected authored commands need it. Retain selected profile/team-source revisions and managed-file conflict behavior during repeated enrollment/render/update. The engine contributor project's own required commands are not automatically installed into a downstream repository.

## Verification, docs and open inputs

Windows CI invokes native PowerShell bootstrap and executes required portability/service tests plus generated generic/Python positive/negative journeys with `sh`/WSL unavailable. Mark genuinely Unix-only tests by platform with explicit reasons and matching retained Unix jobs; do not make every problematic test a skip. A Windows job must include lock/file safety tests, actual command execution and reproducible setup. Run candidate consumer installation from built wheel/hashed assets before release authorization; published-asset replay remains read-only under existing release workflow rules. Include a bare seed and a generated project, verify identical manifest identity and clean tracked state after checks, and bind receipts to exact revision/artifact/source identities.

Before claiming Windows 11 x64 qualification, perform the same journey on a clean Windows 11 x64 account in native PowerShell, record OS/shell/tool versions and source/wheel identity, spaces/Unicode, repeated setup, fresh terminal activation, concurrent writes, edited managed file conflict, interruption/sharing failure and retry. Keep native desktop recognition/authentication not-assessed until the separately owned installed-client smoke test supplies evidence. Extend existing platform qualification tracking (#53) with this evidence rather than reclassifying historical Unix passes.

The implementation may proceed before a Windows desktop host or exact Antigravity edition is selected; qualification cannot be marked passed until observed. Maintainer plus affected teammate own those inputs. Corporate winget/profile restrictions may change the accepted installation route, never the security/ownership contract. Exact reviewed upstream checksums and compatible release version are implementation/release inputs to fill before shipping; this design intentionally contains no fabricated hashes or promised release number.

Review/update current canonical setup, architecture/runtime and release documents through docs/index.md and docs/catalog.toml; maintain source/template and package inclusion parity. Record required content-bound dispositions. Add only real evidence to verification records, without a parallel completion report.
