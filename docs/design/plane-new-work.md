# Plane new-work adapter design

Prepared 2026-09-07 from current official documentation and pinned public source. No Plane installation, deployment, account access or service mutation occurred. This child starts from the frozen Jira candidate e377d720.

## Scope

Implement one optional trusted `plane` tracker definition with explicit `deployment = "cloud" | "self_hosted"`, current `/api/v1/.../work-items/` REST contract, new-work create/find/read/transition/link/capabilities, and the accepted common declarative connection handler. GitHub/Jira projects must remain fully usable without a Plane token, binary, server, or configuration. This is configuration portability for future work, not migration of existing tickets or a live GitHub-to-Plane swap. #21 remains outstanding.

The separate PN-01–05 child spec preceded code. It must update the toolset-composition TC-02 case and `lifecycle_available` declaration, which currently truthfully describe Plane as lacking an adapter. Preserve a test proving absent optional Plane access has no effect on selected GitHub/Jira. Do not add provider switches to CLI, provisioning, or WorkService, and do not relax existing finish gates.

## Verified API facts and practical decisions

- [API introduction](https://developers.plane.so/api-reference/introduction): Cloud API origin is `https://api.plane.so`; self-hosted origin depends on deployment. PAT uses `X-API-Key`; externally obtained OAuth uses Bearer. Both can use a named local `token_env`, with explicit `auth_mode` and no token inference, login extraction, refresh, or secret persistence. The current fetched pages consistently use cursor/per_page pagination; older indexed snippets showing offset/limit must not drive implementation. No claim is made about a particular installed self-hosted release.
- [Current user](https://developers.plane.so/api-reference/user/get-current-user): GET `/api/v1/users/me/`, scope `profile:read`, supplies account ID. Require it to match configured account UUID during discovery and each lifecycle invocation.
- [Project list](https://developers.plane.so/api-reference/project/list-projects) and [project read](https://developers.plane.so/api-reference/project/get-project-detail): GET `/api/v1/workspaces/{workspace_slug}/projects/` and `/{project_id}/`, scope `projects:read`. Require explicit workspace slug; discover project UUID and identifier. Bind observed workspace UUID where returned by the full serializer; do not invent a workspace-list endpoint. Validate selected project and any returned parent IDs on later reads.
- [Create](https://developers.plane.so/api-reference/issue/add-issue): POST project `/work-items/`; documented fields include `name`, `description_html`, `state`, `external_source`, `external_id`, and optional `type_id`. Scope `projects.work_items:write`. Restrict first child to ordinary new work items; omit type selection, custom properties, assignees, labels, sub-items, migration fields and integrations unless specifically scoped and validated. Required custom organizational workflow should refuse with actionable guidance, not guess field values.
- [Read](https://developers.plane.so/api-reference/issue/get-issue-detail) and [list](https://developers.plane.so/api-reference/issue/list-issues): `/work-items/{uuid}/` and `/work-items/`, scope `projects.work_items:read`. List contract has `cursor`, `per_page` (max 100), `next_cursor`, `next_page_results`, counts and results. Use complete bounded cursor enumeration for correlation recovery. Do not treat a first page, API error, archived/missing scope, malformed envelope, duplicate UUID, repeated/missing cursor, or exhausted budget as proof of absence. Correlation-filtered lookup has an important source difference below.
- [States](https://developers.plane.so/api-reference/state/list-states) and [state groups](https://developers.plane.so/api-reference/state/overview): project `/states/`, scope `projects.states:read`; native groups are backlog, unstarted, started, completed, cancelled. Explicit distinct UUID mappings: open→backlog/unstarted, in_progress→started, closed→completed, cancelled→cancelled. A cancelled result must never satisfy successful closure.
- [Update](https://developers.plane.so/api-reference/issue/update-issue-detail): PATCH work item with `state` UUID, scope `projects.work_items:write`. Re-read current item/state catalog before mutation; patch only state; validate target belongs to selected project and expected group; verify result afterwards. No title/description rewriting, blanket Done interpretation, silent terminal reversal, or stale mapping assumptions.
- [Create link](https://developers.plane.so/api-reference/link/add-link) and [list links](https://developers.plane.so/api-reference/link/list-links): project work-item `/links/`, POST URL and optional title, GET cursor pages; scopes `projects.work_items.links:write` and `projects.work_items.links:read`. Preserve authored description and existing links. Exact URL under exact tenant/project/item is the reconciliation identity. The documented payload has no Jira-style globalId/idempotency key; do not fabricate one in metadata.

Configuration should require separate explicit API and web origins for self-hosting, plus deployment, workspace slug, account UUID, project UUID/identifier, four state UUIDs, auth mode and env reference. Bare HTTPS origins are supported; explicit self_hosted HTTP localhost and literal loopback IPv4/IPv6 origins are also supported with strict port validation. Custom subpath hosting is outside this child. Cloud origins can be validated against documented Cloud values. Requests must stay on configured API origin, never follow authentication redirects, and never derive an authenticated target from a returned URL. Ticket references must retain tenant/project/item identity. The browser permalink is based on the pinned official frontend route linked below; API reference docs alone do not establish that route. An explicit user-supplied web origin is a declaration, not proof of association with an API deployment.

## Source evidence that narrows the promises

Pinned public Plane commit: `1fec307f91003df96351557af32ce87891a3678a` (preview, retrieved read-only). This is source evidence, not a released-version or hosted-deployment qualification.

1. [Work-item/link views](https://github.com/makeplane/plane/blob/1fec307f91003df96351557af32ce87891a3678a/apps/api/plane/api/views/issue.py): `IssueListCreateAPIEndpoint.get` uses a singleton lookup when both external keys are passed; duplicate entries could therefore fail instead of producing a page. Its ordinary list and link list use read replicas. Create checks an existing external pair before saving and returns a conflict with ID. These are useful reconciliation affordances, not evidence of atomic uniqueness.
2. [Serializers](https://github.com/makeplane/plane/blob/1fec307f91003df96351557af32ce87891a3678a/apps/api/plane/api/serializers/issue.py): work-item descriptions are parsed and sanitized; `description_stripped` is excluded from the serializer. Link creation checks for an existing URL before insert, and accepts title/URL rather than writable metadata. Thus require a visible escaped-text correlation paragraph inside description_html; do not rely on HTML comment retention or description_stripped. Decode HTML text exactly and cross-check the external pair. Reuse matching links without overwriting titles.
3. [Models](https://github.com/makeplane/plane/blob/1fec307f91003df96351557af32ce87891a3678a/apps/api/plane/db/models/issue.py): inspected Issue/IssueLink models do not declare uniqueness of the external pair or issue/URL pair. Do not claim cross-machine exactly-once creation or links from these prechecks.

Recommended correlation: reserve external_source `ai-dlc`; derive external_id from stable project/work correlation plus tenant/project scope; write both in the initial create request with the exact WorkService correlation as visible escaped HTML text. Confirm all three after create and when finding existing work. Never use an upsert that could overwrite an authored item. Duplicate matches, mismatched markers/external pairs, lost create responses and temporarily invisible records retain uncertainty. Existing WorkService publish journal already prevents an uncertain create retry; fixtures must exercise that real service path.

## Accepted recovery ruling and concrete construction (approved)

Parent ruled that Plane must never retry an uncertain create/link solely because replica-backed reads show absence. An adapter-owned durable attempt ledger is authorized; no WorkService change or new public mutation/recovery API is authorized.

Constructor: `PlaneProvider(config, *, root=None, state_home=None, environ=None, transport=None, selected=True)`. Production central registration passes the resolved Registry root into the bundled executable as a separate internal argument, alongside provider JSON configuration. `main` constructs the provider with that explicit root. Root/storage overrides must not be accepted from tracked provider configuration or the wire payload. Transport injection is a Python HTTP-fixture seam. CLI and WorkService remain vendor-neutral. Direct construction without root supports reads/discovery/capabilities but refuses every mutation before a network write.

Storage: `${XDG_STATE_HOME:-$HOME/.local/state}/ai-dlc/provider-attempts/plane/<digest(canonical-root-path)>/<digest(operation_id)>.json`, outside shared project files and independent of the WorkService operations table. Resolve the state base from the Registry's explicit environment, reject relative state roots, and pass the selected absolute location through the same internal invocation context. Open/create a private owner-controlled directory and regular ledger; reject symlink components, hardlinked/foreign/writable ledger files, unavailable paths, schema mismatch and corruption. Do not silently fall back to another ledger. The approved refinement uses immutable files instead of SQLite: pinned directory descriptors and a directory lock coordinate an exclusive no-follow create. Intent bytes and the containing directory are synced before sending. Existing bytes must exactly match the complete expected record, including its scope/payload fingerprint. Files are never replaced, removed, reset or updated to cache success. PlaneAttemptStore rechecks directory/file identity before writes and successful reconciliation.

Ledger file key: supplied operation_id within this root's Plane namespace. Stored fingerprint binds canonical root, deployment/API origin, web origin, account UUID, workspace slug/observed UUID, project UUID/identifier, operation, stable work correlation or ticket UUID, and canonical payload digest. Never store credentials, email, token hashes, headers or raw server error bodies. State mappings relevant to a transition belong in its fingerprint. Same operation_id with changed root/account/tenant/work/payload refuses. Separate files must not be used to disguise retry of an existing operation. Root relocation, deleted local state, a new machine, or a deliberately new operation_id is outside the original durable guarantee and must be called out, never presented as restored uncertainty knowledge.

Mutation algorithm:

1. Validate configuration, authenticated identity, project/state metadata and safe storage. Validate an existing intent fingerprint or durably create the intent before any mutation result is reconciled. Read exact remote matches completely; duplicate/conflicting matches refuse.
2. Only the exclusive intent-file creation winner may send, after syncing the file and directory and rechecking identity. A prior matching intent permits read reconciliation only, including after a crash. A single existing exact result is returned without writing.
3. Return a successful result only when scoped remote read-back establishes the outcome; retain the immutable intent. A transport loss, timeout, malformed successful response, failed read-back or crash leaves pending/uncertain. On any later attempt, one exact result can reconcile; absent/incomplete/conflicting results refuse. No automatic intent clearing, mutation retry or record deletion. Even a failure known before sending after intent insertion may conservatively require inspection rather than infer retry safety.
4. The same policy covers state PATCH; a current target state may reconcile only with the correct scoped ticket/correlation and unchanged intended target. A changed terminal outcome must not be overwritten. Previous successful operations are validated against current remote evidence when the operation is explicitly re-entered; authored later changes are not silently undone.

For links, reconciliation is exact URL + exact scoped ticket; preserve authored title and description. Existing server URL prechecks remain supplemental, with no claimed atomic uniqueness. A matching existing authored link can satisfy the requested link without claiming AI-DLC authored it. For create, verify same-create external pair plus exact visible correlation; ordinary complete cursor scanning detects duplicates that singleton external lookup cannot safely enumerate.

Direct/manual behavior: the ordinary `ai-dlc work ...` flow supplies stable operation IDs and trusted runtime context. A direct JSON subprocess invocation lacking the internal root/state context refuses create/link/transition. An authorized integrator can use the trusted Python constructor with an explicit root and stable operation_id and receives identical ledger protection; no ledger-free mode is supplied. An unresolved diagnostic identifies the nonsecret operation ID, ticket/project and expected correlation or URL, tells the operator to inspect Plane and retain the ledger, and says rerunning will only reconcile. There is no force-retry switch. If no outcome can be established, it remains blocked; additional general recovery UX is outside this child.

Lost-response and local-safety test matrix:

| Case | Required result |
| --- | --- |
| Intent committed, crash before request | Retry reads only; absent result remains blocked |
| POST accepted, response lost, replica initially empty | No second POST; later exact read reconciles |
| Link accepted, response lost, later invocation via real WorkService | Existing outer journal reinvocation is stopped at Plane ledger; no duplicate POST |
| Server rejects/429/5xx after durable intent | No automatic resubmission; actionable unresolved diagnostic |
| Read-back malformed, partial, rate-limited or budget-exhausted | Uncertain, never absence evidence |
| Duplicate marker/external pair or duplicate exact links | Refusal, no arbitrary first match |
| Two processes use the same operation ID | Atomic insert permits at most one sender; other only reconciles |
| Same ID changes token account, origin, project, work or URL | Fingerprint/identity refusal before any mutation |
| Corrupt/unwritable/symlinked ledger, missing explicit root | Refusal before network mutation; no fallback path |
| Successful state changed by another actor | Never replay stale PATCH or convert cancellation to success |
| New root/machine or deliberately deleted ledger | Explicit evidence limitation; no cross-machine exactly-once claim |

## Proposed acceptance and qualification

TDD transport fixtures should cover both explicit auth modes and origins; identity/redirect/foreign references; complete multi-page discovery and recovery; API budgets, duplicate/cyclic/malformed pages; same-create marker/external keys and HTML sanitization; lost create response with real WorkService journal preventing retry; disjoint cancelled/completed behavior; state changes/unknown mappings/terminal guards; exact-URL authored link preservation, concurrent duplication refusal and uncertain-link decision above. Exercise real Registry+WorkService publish/start/link/finish with fixture SCM/CI evidence clearly labeled, plus common discover/select/save/apply authored-safe stale-plan refusal and generic CLI registration.

Run all required checks and strict OpenSpec on an immutable candidate, then independent review. Success establishes fixture contract implementation only. Real Plane deployment/version/edition, base and web origins, account token grants, selected workspace/project/state policy, server behavior, proxy/TLS behavior, permissions and a live swap remain explicit external evidence. [Self-hosting documentation](https://developers.plane.so/self-hosting/overview) does not establish that the user has a deployment; none is available or requested here. Parent #20 and #21 status must retain their undelivered live/Plane scope until separately decided.
